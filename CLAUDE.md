# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # runs Express API (localhost:8787) + Vite frontend (localhost:5173) together, via concurrently
npm run dev:server    # Express API only
npm run dev:client    # Vite frontend only
npm run build         # production frontend build (vite build -> dist/)
npm test              # runs both test files in sequence
node test/decision.test.js    # run a single test file directly
node test/techMatch.test.js   # run a single test file directly
```

There is no lint script and no test framework — `test/*.test.js` are plain Node scripts using `node:assert`, each ending with a `console.log('...: all checks passed')`. They exercise the two rule-based engines (`decision.js`, `techMatch.js`) with no network calls, so they run instantly and don't need API keys.

Requires a local `.env` (gitignored; copy `.env.example`) with `FIRECRAWL_API_KEY` and `HUBSPOT_PRIVATE_APP_TOKEN` — anything that hits `/api/process` or `/api/tech-scan` will fail without both. The Vite dev server proxies `/api/*` to `localhost:8787` (see `vite.config.js`).

Deployed on Vercel (auto-deploys on push to `main` of `amitsharma-bit/GD-Mapping-Dashboard`). `api/index.js` re-exports the Express app from `server/index.js` as a single Vercel serverless function — an Express app is itself a valid `(req, res)` handler, so no adapter is needed. `vercel.json` sets `maxDuration: 60` on that function and rewrites `/api/*` to it, everything else to `index.html` (SPA fallback).

## Architecture

Single Express backend + single-page React (Vite, no router) frontend, two independent features sharing infrastructure. `App.jsx` is a bare `useState` tab switcher between them — no other global state.

### Two pipelines

**Dealership Group Mapping** (`server/lib/pipeline.js`, UI: `DealershipMappingTab` + `ResultsTable`) — given a domain, determines its ultimate dealership-group ownership and checks it against HubSpot, read-only:

0. **Check HubSpot's own data FIRST, before any external research.** `findCompanyByDomain()` (`hubspot.js`) fetches `dealership_group_name` on the dealership's own Company record - if that's already set, `processDomain()` short-circuits immediately: confidence 100, `MAP` (or `REVIEW` if no matching group *record* exists under that exact name), done in ~5-10s with zero external calls. **This was the single biggest bug found in this pipeline** - the property was already being fetched but never read, so an already-correctly-tagged company still went through external web research and got reported unmapped whenever that research (which depends on the *dealership's own website* self-disclosing ownership) came up empty. Verified live against two real, already-tagged dealerships. If you're debugging "why does X show unmapped," check this path first - it's almost certainly cheaper to fix here than in the research pipeline below.
1. Only when HubSpot doesn't already know: `firecrawl.js: extractOwnership()` — Firecrawl's `/v2/scrape` with a `json`-format extraction (LLM-based, but synchronous - one request, no polling), homepage only. **This used to be `/v1/extract` batching up to 10 candidate pages** but that endpoint stopped working entirely — verified live, every job failed with "All provided URLs are invalid" regardless of URL validity — and `/v2/scrape` is single-URL only, so checking 10 pages per domain isn't affordable under the rate limit below anyway. **Firecrawl's extraction LLM fills unstated fields with placeholder text** ("Not stated", "N/A") despite the prompt saying not to - `firecrawl.js: scrubNotStated()` scrubs this at the source so it never flows downstream as if it were real data (verified live: `owner`/`dealer_principal` came back as the literal string `"Not stated"` before this fix).
2. `firecrawl.js: searchWeb()` — two consolidated OR-queries (was 3 separate ones) covering ownership language, acquisitions, and trade-press sources (Automotive News/PR Newswire/Business Wire) — see the rate-limit note below for why they're merged rather than separate. `pipeline.js: mineGroupMention()` mines a candidate group name out of result snippets against a broadened set of `MENTION_PATTERNS` (acquisition language, executive-title sentences, "X family of dealerships", not just the original 3 rigid phrasings) - **broadening this increases recall but also noise** (verified live: it correctly found a real "Go Auto Group" mention, but from an unrelated general industry M&A tracker page, and a separate noisy fragment conflicted with it - the conflict-detection below caught this and returned a low-confidence `REVIEW` rather than guessing, which is the safety net doing its job, not a failure).
3. **Owner-name fallback** (`pipeline.js`, only fires when steps 1-2 found nothing at all): if the site named an `owner`/`dealer_principal`, one more query searches that *person's* name for a group affiliation. This is a deliberately narrow, one-hop approximation of "does this owner run other dealerships under a known group" - the full version (finding every other dealership the same person owns, then determining *their* group) would need re-running this whole pipeline against each of those other domains, which isn't affordable in one request under the rate limit below.
4. **Group-site verification** (`pipeline.js: verifyAgainstGroupSite()`, only fires when a candidate exists): opportunistically identifies the candidate group's own official site from URLs already fetched in step 2 (`findLikelyGroupSite()` - compares each URL's registrable domain against the candidate name via `namesLikelyMatch`, skipping a hardcoded list of known non-corporate hosts like press wires and LinkedIn) and fetches it once to check whether this dealership's name or domain is actually listed there. A **confirmation-only** signal - if verification is attempted but inconclusive, confidence is never reduced, only ever boosted, because the verification mechanism itself is an approximation and shouldn't penalize a real dealership for our failure to confirm it.
5. `decision.js: decideOwnership()` — pure rule-based scoring, no LLM. Base confidence depends on *how* the candidate was found (`official_site`=70, `search_mined`=60, `owner_fallback`=55 - first-party site claims are more reliable than third-party search snippets, which are more reliable than a name found two inferential hops away via the owner's name); each *independent* corroborating source adds 15; confirming against the group's own site (step 4) adds another 15; any source naming a conflicting group forces `REVIEW` at low confidence regardless of the math. `confidence >= 95` → `MAP` (if a matching HubSpot group exists) or `CREATE_NEW_GROUP`; `90–94`, `80–89`, and `<80` all resolve to `REVIEW`, differing only in the `reason` text - this MAP threshold is unchanged from the very first version of this tool, deliberately, since loosening it would directly increase false positives.
6. `hubspot.js: findGroupCandidates()` — read-only HubSpot Company search. **Important non-obvious fact:** "Dealership Group" is not a HubSpot custom object — it's a free-text Company property, `dealership_group_name`. A group's "record" is just the Company whose own `name` happens to equal its `dealership_group_name`. Matching is fuzzy (`normalize.js: namesLikelyMatch`) specifically because the same group appears under aliases (e.g. "Lithia" / "Lithia Motors" / "Lithia & Driveway") — exact-string matching was tried and failed in production testing. **The fuzzy matching has a sharp edge:** generic industry words (`motors`, `group`, `automotive`, `auto`, `inc`, `llc`, `corp`) must be stripped in `normalizeCompanyName`'s `LEGAL_SUFFIXES`, or two *unrelated* companies that both just say e.g. "Automotive" in their name become a false-positive match — this happened live ("Sonic Automotive" matched "Battlefield Automotive" at 100% confidence) before `automotive`/`auto` were added to that list. If you add more stripped words, re-run `test/decision.test.js` — the regression test for exactly this bug is in there.
7. The app **never writes to HubSpot** — this was an explicit product decision. Output is a recommendation only.
8. **What's deliberately NOT implemented**, despite being asked for, because it isn't affordable under the rate/timeout constraints below or requires integrations this app doesn't have: full multi-hop "find every other dealership the same owner runs, then determine each of *their* groups"; crawling the parent group's entire site to extract its full location roster (only a single-page presence check, see step 4); direct LinkedIn/SEC-EDGAR/DealerRater/state-dealer-association API lookups (only whatever a general web search's snippets surface about those sources); HubSpot corporate-phone-number matching (no phone data is stored on the HubSpot side to compare against yet).

**Technology Intelligence Agent** (`server/lib/techDetect.js`, UI: `TechIntelTab` + `TechResultsTable`) — given a domain, fingerprints its martech/DMS/CRM stack across 8 categories (website_provider, chat, reputation, crm, scheduling, ims, dms, analytics; plus digital_retail/inventory/other, detail-view-only):
1. **Page discovery, not homepage-only.** `techDetect.js` fetches the homepage via `firecrawl.js: scrapePage()` (single synchronous `/v2/scrape` call) **and, concurrently, calls `crawlSite()` with `includePaths` set to `PAGE_DISCOVERY_PATTERNS`** - keyword-substring regexes (about/contact/inventory/new/used/finance/trade/sell/service/parts/body/privacy/terms/login/portal) covering every page type the detection rules care about. **Verified live against a real dealer site: `includePaths` correctly steered the crawler to real pages like `/schedule-service/` and `/parts/`** that an unscoped crawl was missing entirely (it wandered into arbitrary linked content like staff bios instead). The homepage fetch is separate and mandatory because `includePaths` **excludes the root path** if `/` doesn't itself match one of the patterns - the homepage still carries most sitewide signals (analytics, chat, website-provider markers) that already worked well, so it can't be dropped just to reach `/service`.
2. `htmlSignals.js` — regex extraction (not a DOM parser — deliberately, see file comment) of: script/iframe `src` URLs, inline script content, JSON-LD blocks, full `<form>...</form>` blocks (not just `action=` — this is what catches a vendor named only in a *hidden input's value*, which the user explicitly asked for), `<link rel=stylesheet href>` URLs, and Firecrawl's own `markdown` format (clean page text, used only for footer-credit matching below). Anchor hrefs (`linkHrefs`) come straight from Firecrawl's `links` format — no need to regex those ourselves.
3. `techMatch.js` + `techSignatures.js` — each vendor declares ONE `domain` regex (see `techSignatures.js`'s top comment) plus an optional `namePattern` (the vendor's plain *name*, for footer credits) and optional `metaExtra`. Checked against **every** evidence source, tiered by how strong a signal each source is:
   - **100 ("strong")**: script src, iframe src, inline script content, OR a footer **"Powered by X" / "Designed by X" / "Website by X" / "Inventory by X" credit** (`techMatch.js: findCreditMatch` — requires the vendor's name within 60 chars of one of those phrases in the page's markdown text, not just both appearing anywhere on the page, specifically to avoid e.g. "Reynolds" as someone's last name in a testimonial counting as a Reynolds & Reynolds credit — there's a regression test for exactly this in `techMatch.test.js`). A footer credit is the site's own first-party claim about its platform, arguably *more* authoritative than an incidentally-loaded third-party script, hence the same top tier.
   - **95/90 ("moderate")**: page metadata / JSON-LD, ≥2 distinct hits vs. 1.
   - **80 ("indirect")**: a lead-capture form's `action=` *or any hidden input inside it*, a stylesheet href, or a plain link href — could just be a footer link to the vendor's marketing site, still real evidence though.
   - Zero hits anywhere → **not reported at all** (never guesses — no sub-80 "possible" tier, since below-80 would mean no evidence at all exists).
   This broad multi-source check (not just `<script src>`) is what makes CRM/Service Scheduler/IMS/DMS detection viable at all — those tools are frequently just a "Schedule Service" link, a footer credit line, or a lead-capture form's `action=`/hidden field, never a sitewide script. `techSignatures.js` is explicitly a best-effort, extensible list; a vendor not in it is a silent false negative, never a fabricated positive - a few requested vendors (Auto/Mate, Inventory+, Simple Scheduler) were deliberately left out because their real domains aren't confidently known and their names are too generic to guess without real risk of a false-positive collision with an unrelated site. Some entries (CDK, Reynolds, Tekion, DealerSocket, Dominion) intentionally appear under *multiple* categories (crm/dms/scheduling) with the *same* domain regex — these vendors genuinely sell CRM+DMS+Scheduler as one platform, and there's no way to tell which module is actually in use from the domain alone.
4. Company name / country / state / `is_us_dealership` are read only from JSON-LD structured data (`techDetect.js: determineGeo`) — never inferred from page prose. `is_us_dealership` defaults `true` absent contrary evidence (a non-US ccTLD or explicit non-US address) rather than requiring positive proof, since a missing address isn't evidence either way.
5. **Real ceiling, not a bug — verified live, not just theorized:** on a real dealer site's contact page, the lead-capture form was a Gravity Forms plugin that POSTs *back to the site's own domain*, not to any external CRM's endpoint - the actual CRM handoff happens entirely server-side, invisible to any public crawler no matter how good the evidence-source coverage gets. Many dealership CRM/DMS systems are 100% internal/backend tools with zero public-website footprint. An empty CRM/DMS column can be a correct "no evidence exists to find," not a detection failure - don't chase 100% coverage as if every empty cell must be a bug.

### The constraint that shapes both pipelines

This account's **Firecrawl plan is rate-limited to 5 requests/minute, TOTAL, across every endpoint** (extract, search, crawl, and their status-poll GETs), and the app targets **Vercel Hobby's 60-second function timeout** (`vercel.json: functions.maxDuration`). Several design choices exist specifically because of this — don't "simplify" them away without re-reading why:
- **Every outgoing Firecrawl request is paced through a shared gate** (`firecrawl.js`: `throttle()`/`MIN_INTERVAL_MS = 13000`) that enforces ≥13s between requests, globally, regardless of how many callers fire "concurrently" via `Promise.all`. This didn't exist originally — without it, a single domain's own poll loop plus parallel corroboration searches could attempt 15-25 requests in under a minute and 429 almost immediately, which is exactly what happened in production. The gate is implemented as a promise chain (not a plain "check timestamp, then wait" function), because a naive version lets concurrent callers race and all read the same stale timestamp before any of them updates it — defeating the gate specifically in the `Promise.all` case it needs to handle.
- On a 429, `withRetry()` parses Firecrawl's actual `"retry after Xs"` text and waits that long, rather than a blind fixed backoff.
- Both `extractOwnership()` (now a single `/v2/scrape` call, no polling) and `crawlSite()` bound their work to fit this pacing within Vercel's 60s ceiling. `crawlSite()`'s poll loop checks `Date.now() + MIN_INTERVAL_MS <= deadline` (not just `Date.now() < deadline`) before each poll — otherwise the gate can block a poll past its own deadline once already committed to it.
- `pipeline.js`'s `CORROBORATION_QUERIES` is capped at 2 consolidated OR-queries (was 3 separate, briefly 5) — at 13s/request, each additional query costs ~13s against the 60s ceiling. The owner-fallback and group-site-verification steps each cost one more gated call but are mutually exclusive in practice (verification only runs when a candidate already exists; the owner fallback only runs when one doesn't), so the pipeline's worst case is still ~4 gated calls (extract + 2 queries + one of the two optional steps) even though there are 4 possible call sites. The HubSpot-short-circuit path (see pipeline step 0 above) skips all of this and costs one gated call total.
- The frontend processes bulk batches (paste list / CSV / Excel, parsed client-side in `src/lib/parseFile.js` using `xlsx` for both formats) **one domain at a time, sequentially** — this is deliberate rate-limit pacing, not a missed optimization opportunity.
- `/v1/crawl` was chosen over N separate `/v1/scrape` calls in the tech-intel pipeline for the same reason.
- The tech-intel pipeline now makes **two** Firecrawl calls (`scrapePage()` for the homepage + `crawlSite()` for everything else, dispatched via `Promise.all` but still serialized 13s apart by the gate underneath) instead of one, so `crawlSite()`'s default `budgetMs` was cut from 52000 to 40000 to compensate and stay under Vercel's 60s ceiling.
- If you raise `CORROBORATION_QUERIES`, `limit` in `crawlSite()`, or add pages back to either pipeline, re-check the total-request-count math against `MIN_INTERVAL_MS` and Vercel's timeout — it's easy to silently blow one or the other again.
- **Separate from rate limiting:** the Firecrawl account can also return `402 Insufficient credits` on *every* endpoint (verified live - even `limit: 1` failed) when its plan credit balance is exhausted, which no amount of pacing/retry logic can work around. If every request suddenly fails, check for a 402 before assuming the rate-limit gate broke.

### Frontend state

No global store. Each tab component (`DealershipMappingTab`, `TechIntelTab`) owns its own results in `useState`, persisted to its own `localStorage` key (`gd-mapping-results`, `gd-tech-intel-results`) so a batch survives a page refresh — completed domains are skipped on re-run, incomplete ones resume. Styling is a single global stylesheet (`src/styles.css`, design tokens as CSS custom properties) with plain `className`s — no CSS-in-JS, no Tailwind.
