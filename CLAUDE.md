# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev          # runs Express API (localhost:8787) + Vite frontend (localhost:5173) together, via concurrently
npm run dev:server    # Express API only
npm run dev:client    # Vite frontend only
npm run build         # production frontend build (vite build -> dist/)
npm test              # runs both test files in sequence
node test/decision.test.js    # run a single test file directly
node test/techMatch.test.js   # run a single test file directly
```

There is no lint script and no test framework — `test/*.test.js` are plain Node scripts using `node:assert`, each ending with a `console.log('...: all checks passed')`. They exercise the two rule-based engines (`decision.js`, `techMatch.js`) with no network calls, so they run instantly and don't need API keys.

Requires a local `.env` (gitignored; copy `.env.example`) with `ANTHROPIC_API_KEY` and `HUBSPOT_PRIVATE_APP_TOKEN` for `/api/process` (Dealership Group Mapping), and `FIRECRAWL_API_KEY` and `HUBSPOT_PRIVATE_APP_TOKEN` for `/api/tech-scan` (Technology Intelligence Agent — still Firecrawl-based, unchanged). `ANTHROPIC_MODEL` is optional (defaults to `claude-sonnet-5`). The Vite dev server proxies `/api/*` to `localhost:8787` (see `vite.config.js`).

Deployed on Vercel (auto-deploys on push to `main` of `amitsharma-bit/GD-Mapping-Dashboard`). `api/index.js` re-exports the Express app from `server/index.js` as a single Vercel serverless function — an Express app is itself a valid `(req, res)` handler, so no adapter is needed. `vercel.json` sets `maxDuration: 60` on that function and rewrites `/api/*` to it, everything else to `index.html` (SPA fallback).

## Architecture

Single Express backend + single-page React (Vite, no router) frontend, two independent features sharing infrastructure. `App.jsx` is a bare `useState` tab switcher between them — no other global state.

### Two pipelines

**Dealership Group Mapping** (`server/lib/pipeline.js`, UI: `DealershipMappingTab` + `ResultsTable`) — given Company Name + Domain + City + State, determines the dealership's CURRENT corporate ownership via real Claude-driven web research (no Firecrawl anywhere in this module) and checks it against HubSpot, read-only. Rewritten from a Firecrawl+regex pipeline to a Claude + native web_search/web_fetch pipeline — see git history before this rewrite if you need the old approach for reference.

0. **Check HubSpot's own data FIRST, before any external research** (unchanged from the original design). `findCompanyByDomain()` (`hubspot.js`) fetches `dealership_group_name` on the dealership's own Company record - if that's already set, `processCompany()` short-circuits immediately: confidence 100, `MAP` (or `REVIEW` if no matching group *record* exists under that exact name), zero research calls. This is still the cheapest and most reliable path and must run before anything below.
1. Only when HubSpot doesn't already know: `research.js: researchCompany()` sends ONE `messages.create()` call to Claude (`ANTHROPIC_MODEL`, default `claude-sonnet-5`) with the `web_search_20260209` and `web_fetch_20260209` server tools declared, plus a custom `submit_research_report` tool whose JSON schema is the forced final-answer shape (verified company name, owner, dealer principal, parent company, dealer group, acquisition history, related dealerships, official group site, independence, conflicts, evidence with per-item source tier, sources, and the actual queries run). Because web_search/web_fetch are *server-side* tools, Claude's own multi-query iterative research (section 3-11 of the product spec: initial broad queries -> owner-name follow-ups -> group-name follow-ups -> group-site verification) happens **inside that single request** - `pipeline.js` does not hand-drive individual search queries the way the old Firecrawl version had to.
2. **`pause_turn` resume loop**: the server-side tool loop has an internal iteration cap: if Claude hits it before calling `submit_research_report`, the response comes back with `stop_reason: 'pause_turn'`. `research.js` resumes by re-appending `{role:'assistant', content: response.content}` and re-calling (no synthetic "continue" user message - the API auto-detects the trailing `server_tool_use` block), capped by `MODE_CONFIG[mode].maxRounds` as a runaway-cost backstop.
3. **Ground-truth verification, not just trusting the model's self-report**: `research.js: collectGroundTruth()` scans every `web_search_tool_result`/`web_fetch_tool_result`/`server_tool_use` block actually returned across the whole exchange and extracts the real URLs/queries via a permissive regex (deliberately not coded to an exact nested SDK type, since the point is "did this URL really come from a tool call"). `sanitizeReport()` then drops any evidence item or source the model claims but that never actually appeared in a real tool result - this is the concrete enforcement of "never fabricate research results" rather than a prompt-only promise.
4. Three research modes (`MODE_CONFIG` in `research.js`) trade search budget/effort for speed: `quick` (3 searches, low effort), `standard` (6 searches, medium effort, the default), `deep` (14 searches, high effort - an explicit user-triggered escalation from the UI when Standard's confidence is low, since it's the only mode that risks exceeding Vercel's 60s ceiling; see the constraints section below).
5. `decision.js: decideMapping()` — pure rule-based scoring over the *verified* evidence array, no LLM self-assessment used for confidence. Confidence depends on the tier (`tier1`=official site/OEM locator/press release/gov record, `tier2`=trade press/reputable local news, `tier3`=LinkedIn/directories) and count of independent surviving evidence items, plus whether Claude actually `web_fetch`'d the candidate group's own site and confirmed this dealership is listed there (`group_site_confirms_dealership` -> confidence 100). Any `conflict_detected` forces `REVIEW` at low confidence regardless of the rest of the math. `confidence >= 95` -> `MAP` (if a matching HubSpot group exists) or `CREATE_NEW_GROUP`; `80-94` and `<80` both resolve to `REVIEW`, differing only in the `reason` text - the 95 MAP threshold is unchanged from the very first version of this tool, deliberately, since loosening it would directly increase false positives. `decision.js: classifyMatchType()` / `findBestHubSpotMatch()` produce the `EXACT_MATCH` / `NORMALIZED_MATCH` / `ALIAS_MATCH` / `OWNERSHIP_MATCH` / `ACQUISITION_MATCH` / `POSSIBLE_MATCH` / `NO_MATCH` classification shown in the UI.
6. `hubspot.js: findGroupCandidates()` — read-only HubSpot Company search. **Important non-obvious fact:** "Dealership Group" is not a HubSpot custom object — it's a free-text Company property, `dealership_group_name`. A group's "record" is just the Company whose own `name` happens to equal its `dealership_group_name`. Matching is fuzzy (`normalize.js: namesLikelyMatch`) specifically because the same group appears under aliases (e.g. "Lithia" / "Lithia Motors" / "Lithia & Driveway") — exact-string matching was tried and failed in production testing. **The fuzzy matching has a sharp edge:** generic industry words (`motors`, `group`, `automotive`, `auto`, `inc`, `llc`, `corp`) must be stripped in `normalizeCompanyName`'s `LEGAL_SUFFIXES`, or two *unrelated* companies that both just say e.g. "Automotive" in their name become a false-positive match — this happened live ("Sonic Automotive" matched "Battlefield Automotive" at 100% confidence) before `automotive`/`auto` were added to that list. If you add more stripped words, re-run `test/decision.test.js` — the regression test for exactly this bug is in there. `hubspot.js: searchCompaniesByName()` backs the manual "Select HubSpot Group" override control in the UI (`/api/hubspot-groups/search`) - it only ever returns real Company records, so an override can never carry a fabricated record ID.
7. The app **never writes to HubSpot** — this was an explicit product decision. Output is a recommendation only; a user's Approve/Reject/Mark-for-Review/Override decision is stored client-side (`user_decision`, `user_override_group_name`, `user_override_group_id` on the cached result) and is never overwritten by a subsequent re-run (`DealershipMappingTab.jsx: mergeResult()`).
8. **What's deliberately NOT implemented**: full multi-hop "find every other dealership the same owner runs, then determine each of *their* groups" (Claude follows one hop - the owner's name - within the single research call, not a recursive re-run of the whole pipeline per related domain); crawling the parent group's entire site to extract its full location roster (only the single-page presence check in step 5); direct SEC-EDGAR/state-dealer-association API integrations (only whatever `web_search`/`web_fetch` themselves can surface about those sources); HubSpot corporate-phone-number matching (no phone data is stored on the HubSpot side to compare against yet).

**Technology Intelligence Agent** (`server/lib/techDetect.js`, UI: `TechIntelTab` + `TechResultsTable`) — given a domain, fingerprints its martech/DMS/CRM stack across 8 categories (website_provider, chat, reputation, crm, scheduling, ims, dms, analytics; plus digital_retail/inventory/other, detail-view-only):
1. **Page discovery, not homepage-only.** `techDetect.js` fetches the homepage via `firecrawl.js: scrapePage()` (single synchronous `/v2/scrape` call) **and, concurrently, calls `crawlSite()` with `includePaths` set to `PAGE_DISCOVERY_PATTERNS`** - keyword-substring regexes (about/contact/inventory/new/used/finance/trade/sell/service/parts/body/privacy/terms/login/portal) covering every page type the detection rules care about. **Verified live against a real dealer site: `includePaths` correctly steered the crawler to real pages like `/schedule-service/` and `/parts/`** that an unscoped crawl was missing entirely (it wandered into arbitrary linked content like staff bios instead). The homepage fetch is separate and mandatory because `includePaths` **excludes the root path** if `/` doesn't itself match one of the patterns - the homepage still carries most sitewide signals (analytics, chat, website-provider markers) that already worked well, so it can't be dropped just to reach `/service`.
2. `htmlSignals.js` — regex extraction (not a DOM parser — deliberately, see file comment) of: script/iframe `src` URLs, inline script content, JSON-LD blocks, full `<form>...</form>` blocks (not just `action=` — this is what catches a vendor named only in a *hidden input's value*, which the user explicitly asked for), `<link rel=stylesheet href>` URLs, and Firecrawl's own `markdown` format (clean page text, used only for footer-credit matching below). Anchor hrefs (`linkHrefs`) come straight from Firecrawl's `links` format — no need to regex those ourselves.
3. `techMatch.js` + `techSignatures.js` — each vendor declares ONE `domain` regex (see `techSignatures.js`'s top comment) plus an optional `namePattern` (the vendor's plain *name*, for footer credits) and optional `metaExtra`. Checked against **every** evidence source, tiered by how strong a signal each source is:
   - **100 ("strong")**: script src, iframe src, inline script content, OR a footer **"Powered by X" / "Designed by X" / "Website by X" / "Inventory by X" credit** (`techMatch.js: findCreditMatch` — requires the vendor's name within 60 chars of one of those phrases in the page's markdown text, not just both appearing anywhere on the page, specifically to avoid e.g. "Reynolds" as someone's last name in a testimonial counting as a Reynolds & Reynolds credit — there's a regression test for exactly this in `techMatch.test.js`). A footer credit is the site's own first-party claim about its platform, arguably *more* authoritative than an incidentally-loaded third-party script, hence the same top tier.
   - **95/90 ("moderate")**: page metadata / JSON-LD, ≥2 distinct hits vs. 1.
   - **80 ("indirect")**: a lead-capture form's `action=` *or any hidden input inside it*, a stylesheet href, or a plain link href — could just be a footer link to the vendor's marketing site, still real evidence though.
   - Zero hits anywhere → **not reported at all** (never guesses — no sub-80 "possible" tier, since below-80 would mean no evidence at all exists).
   This broad multi-source check (not just `<script src>`) is what makes CRM/Service Scheduler/IMS/DMS detection viable at all — those tools are frequently just a "Schedule Service" link, a footer credit line, or a lead-capture form's `action=`/hidden field, never a sitewide script. `techSignatures.js` is explicitly a best-effort, extensible list; a vendor not in it is a silent false negative, never a fabricated positive - a few requested vendors (Auto/Mate, Inventory+, Simple Scheduler) were deliberately left out because their real domains aren't confidently known and their names are too generic to guess without real risk of a false-positive collision with an unrelated site. Some entries (CDK, Reynolds, Tekion, DealerSocket, Dominion) intentionally appear under *multiple* categories (crm/dms/scheduling) with the *same* domain regex — these vendors genuinely sell CRM+DMS+Scheduler as one platform, and there's no way to tell which module is actually in use from the domain alone.
4. Company name / country / state / `is_us_dealership` are read only from JSON-LD structured data (`techDetect.js: determineGeo`) — never inferred from page prose. `is_us_dealership` defaults `true` absent contrary evidence (a non-US ccTLD or explicit non-US address) rather than requiring positive proof, since a missing address isn't evidence either way.
5. **Real ceiling, not a bug — verified live, not just theorized:** on a real dealer site's contact page, the lead-capture form was a Gravity Forms plugin that POSTs *back to the site's own domain*, not to any external CRM's endpoint - the actual CRM handoff happens entirely server-side, invisible to any public crawler no matter how good the evidence-source coverage gets. Many dealership CRM/DMS systems are 100% internal/backend tools with zero public-website footprint. An empty CRM/DMS column can be a correct "no evidence exists to find," not a detection failure - don't chase 100% coverage as if every empty cell must be a bug.

### The constraint that shapes the Technology Intelligence pipeline

Dealership Group Mapping no longer has a Firecrawl rate limit to work around (Claude's `web_search`/`web_fetch` server tools have no comparable per-account throttle here) - its only remaining constraint is Vercel's 60s function timeout, handled by capping `MODE_CONFIG` search budgets and `pause_turn` resume rounds in `research.js` per mode (`quick`/`standard` are sized to comfortably fit; `deep` is an explicit opt-in escalation that can occasionally exceed it - see pipeline step 4 above). Everything below is specific to the Technology Intelligence Agent, which is unchanged and still Firecrawl-based.

This account's **Firecrawl plan is rate-limited to 5 requests/minute, TOTAL, across every endpoint** (extract, search, crawl, and their status-poll GETs), and the app targets **Vercel Hobby's 60-second function timeout** (`vercel.json: functions.maxDuration`). Several design choices exist specifically because of this — don't "simplify" them away without re-reading why:
- **Every outgoing Firecrawl request is paced through a shared gate** (`firecrawl.js`: `throttle()`/`MIN_INTERVAL_MS = 13000`) that enforces ≥13s between requests, globally, regardless of how many callers fire "concurrently" via `Promise.all`. This didn't exist originally — without it, a single domain's own poll loop plus parallel corroboration searches could attempt 15-25 requests in under a minute and 429 almost immediately, which is exactly what happened in production. The gate is implemented as a promise chain (not a plain "check timestamp, then wait" function), because a naive version lets concurrent callers race and all read the same stale timestamp before any of them updates it — defeating the gate specifically in the `Promise.all` case it needs to handle.
- On a 429, `withRetry()` parses Firecrawl's actual `"retry after Xs"` text and waits that long, rather than a blind fixed backoff.
- Both `extractOwnership()` (now a single `/v2/scrape` call, no polling) and `crawlSite()` bound their work to fit this pacing within Vercel's 60s ceiling. `crawlSite()`'s poll loop checks `Date.now() + MIN_INTERVAL_MS <= deadline` (not just `Date.now() < deadline`) before each poll — otherwise the gate can block a poll past its own deadline once already committed to it.
- The Tech Intel frontend processes bulk batches (paste list / CSV / Excel, parsed client-side in `src/lib/parseFile.js` using `xlsx` for both formats) **one domain at a time, sequentially** — this is deliberate rate-limit pacing, not a missed optimization opportunity. Dealership Group Mapping's `DealershipMappingTab.jsx: runBatch()` also runs sequentially, but for cost/predictability reasons, not to satisfy a rate limit — it has none.
- `/v1/crawl` was chosen over N separate `/v1/scrape` calls in the tech-intel pipeline for the same reason.
- The tech-intel pipeline now makes **two** Firecrawl calls (`scrapePage()` for the homepage + `crawlSite()` for everything else, dispatched via `Promise.all` but still serialized 13s apart by the gate underneath) instead of one, so `crawlSite()`'s default `budgetMs` was cut from 52000 to 40000 to compensate and stay under Vercel's 60s ceiling.
- If you raise `CORROBORATION_QUERIES`, `limit` in `crawlSite()`, or add pages back to either pipeline, re-check the total-request-count math against `MIN_INTERVAL_MS` and Vercel's timeout — it's easy to silently blow one or the other again.
- **Separate from rate limiting:** the Firecrawl account can also return `402 Insufficient credits` on *every* endpoint (verified live - even `limit: 1` failed) when its plan credit balance is exhausted, which no amount of pacing/retry logic can work around. If every request suddenly fails, check for a 402 before assuming the rate-limit gate broke.

### Frontend state

No global store. Each tab component (`DealershipMappingTab`, `TechIntelTab`) owns its own results in `useState`, persisted to its own `localStorage` key (`gd-mapping-results`, `gd-tech-intel-results`) so a batch survives a page refresh — completed domains are skipped on re-run, incomplete ones resume. Styling is a single global stylesheet (`src/styles.css`, design tokens as CSS custom properties) with plain `className`s — no CSS-in-JS, no Tailwind.

`DealershipMappingTab.jsx` additionally supports: bulk input as Company Name/Domain/City/State records (`src/lib/parseFile.js: parseRecordsFromFile()`/`parseRecordsFromText()`, header-synonym detection, column order doesn't matter — see that file's `HEADER_SYNONYMS`); a Quick/Standard/Deep research-mode selector passed straight through to `research.js`; row selection + bulk actions (Research/Deep Research Selected, Retry Failed, Mark Review, Export); a filter+search+sort bar over the in-memory result list (no server-side filtering); and an expandable per-row evidence panel (`ResultsTable.jsx: DetailPanel`) showing the ownership chain, tiered evidence with source links, conflicts, related dealerships, and a HubSpot override search box backed by `GET /api/hubspot-groups/search`. A user's Approve/Reject/Mark-for-Review/Override decision (`user_decision`, `user_override_group_name`, `user_override_group_id`) is preserved across re-runs by `mergeResult()` — research never silently clobbers a human decision.
